# Performance, Parallelism, and Memory Architecture for a B-rep Kernel

Research review supporting the design of Keel, an open-source B-rep solid modeling kernel in Rust with Parasolid-class ambition, at milestone M7b. Keel stores topology in generational-handle arenas (slot-maps), uses copy-on-write persistent topology, requires deterministic results across thread counts as a hard API promise, and keeps analytic geometry exact with NURBS general.

This document is a dedicated study of making the kernel fast and parallel without breaking its correctness, determinism, and topology-mutation invariants. It is the engine-room companion to `kernel/08-kernel-engineering` (which covers BVH/spatial acceleration, testing, and API at survey level) and to `kernel/14-determinism-serialization` (the determinism dossier). It does not repeat BVH construction theory or the determinism-from-predicates argument. It studies data layout, SIMD evaluation, where parallelism is safe, determinism under work-stealing, GPU offload limits, lazy/incremental caching, large-model memory, allocation, scaling, and benchmarking. Full findings per source: citation, technique in explicit detail, limitations, and kernel relevance.

A note on the central tension. A B-rep kernel is two workloads wearing one coat. The numerical workload (surface evaluation, intersection, tessellation, classification, bounding) is embarrassingly data-parallel and SIMD-friendly. The topological workload (Euler operators, merging, the boolean's stitch phase) is a pointer-chasing graph mutation that resists both SIMD and naive parallelism. Every decision below is an attempt to give the first workload everything modern hardware offers while keeping the second workload correct and deterministic. The thesis: parallelize the read-heavy numerical phases aggressively, serialize the write-heavy topology surgery deliberately, and use copy-on-write snapshots as the membrane between them.

## PART 1: Cache-coherent B-rep data layout

### Source: Mike Acton, "Data-Oriented Design and C++" (CppCon 2014)

Citation: Mike Acton (Engine Director, Insomniac Games), keynote, CppCon 2014. Video: youtube.com/watch?v=rX0ItVEVjHc. Slides and code: github.com/CppCon/CppCon2014. Companion: en.wikipedia.org/wiki/Data-oriented_design.

Technique: Acton's thesis is that the purpose of a program is to transform data, so the program should be designed around the data's actual access patterns and the hardware that moves it, not around conceptual object models. Three concrete rules dominate. First, "where there is one, there are many": design for the bulk case, the array, not the single entity. Second, hardware reality is the cache: a main-memory miss costs hundreds of cycles, an L1 hit a few, so the unit of optimization is the 64-byte cache line and the metric is "useful bytes per line touched." Third, separate cold data from hot data: fields touched on every traversal go in one tightly packed array, fields touched rarely (debug names, attribute pointers, provenance) go in a parallel side array so they never evict hot data. The canonical transformation is array-of-structures (AoS) to structure-of-arrays (SoA): instead of `Entity{a,b,c}[]`, store `a[]`, `b[]`, `c[]`. A loop over one field then streams a dense run of that field through cache with zero waste. Acton shows real cases where this layout change alone yields 10x or more, because the bottleneck was never compute, it was memory bandwidth and wasted cache-line bytes.

Limitations: DOD was developed for the regular, homogeneous, frame-recreated data of game engines (particles, transforms, draw calls). B-rep topology is heterogeneous and graph-like: faces point to loops point to coedges that walk radially to other coedges. SoA does not magically linearize a graph traversal whose next node is data-dependent. DOD also trades code clarity for layout control and can ossify a design around one access pattern.

Kernel relevance: This is the foundational lens for Keel's arenas. The slot-map per entity type (vertex, edge, coedge, loop, face, shell) is already a step toward SoA: all faces live contiguously, not scattered on the heap. Keel should push further and split each entity's fields by access frequency. The hot path of a boolean is the coedge/radial walk and box tests; those fields (next/prev coedge indices, partner index, the cached bounding box, the surface handle) belong in one packed hot array. Cold fields (attribute lists, persistent-name tags, history provenance) belong in a parallel cold array indexed by the same handle. The "where there is one, there are many" rule maps directly: classify all sample points of a face in a batch, not one at a time. Acton's discipline is the justification for the SoA-and-hot/cold layout adopted in the synthesis.

### Source: Structure-of-Arrays in Rust (Soak, soa_derive, zerocopy) and ECS layout practice

Citation: Lucien Greathouse, "Soak: a struct-of-arrays library in Rust" (abubalay.com/blog/2019/02/16/struct-of-arrays); `soa_derive` and `soa_rs` crates; ECS-cache analyses such as Jordan Grilly, "CPU Caches: From Theory to Optimization with ECS Examples in Rust"; "Optimizing Rust Data Structures: Cache-Efficient Patterns."

Technique: Rust has no native SoA type, so SoA is achieved either with parallel `Vec`s behind a struct, or with derive macros (`soa_derive`, `soa_rs`) that generate a `Vec`-of-fields container plus indexing methods and an iterator yielding field references. The ECS literature quantifies the payoff: the cache line is 64 bytes, the fundamental unit of every memory fetch; when you iterate millions of entities updating only `position`, AoS drags `velocity`, `mass`, and flags through cache uselessly, while SoA fills each line with positions only. The stated rule of thumb: on memory-bound code the gap between good and bad layout is up to 10x. The literature also gives the decision boundary: use AoS when you almost always touch all fields together and access entities individually (simplicity wins), use SoA when you iterate huge counts touching a field subset. Hot/cold splitting is the refinement: separate frequently-from-rarely-accessed fields into different regions so hot loops never pay for cold bytes.

Limitations: SoA in Rust costs ergonomics. You cannot hand out a `&Entity`; you hand out a generated view struct of field references, which complicates APIs and borrow patterns. Derive macros add compile time and a learning curve. SoA hurts when an algorithm genuinely needs all fields of one entity at once (random single-entity access), where AoS's one-line fetch wins.

Kernel relevance: This is the implementation path for Acton's advice in Keel's language. Keel's slot-maps can be SoA internally: a face arena stores `surface_handle[]`, `outer_loop[]`, `bbox[]`, `flags[]` as parallel vectors keyed by slot index, with cold attribute data in a secondary map. The decision boundary tells Keel where to apply it: the radial/coedge traversal and box-test loops are the high-count, field-subset case that wants SoA, while a one-off "give me everything about this face" interrogation can reconstruct an AoS view. Keel should not blanket-SoA everything; it should SoA the traversal-critical fields and keep the rest in cold storage, exactly the hot/cold split.

### Source: Pointer-chasing in adjacency traversal and the access pattern of boolean imprint/classification

Citation: Synthesis from the half-edge/radial-edge B-rep literature (Weiler radial-edge, Mantyla SMS) cross-read with cache analyses above; reinforced by `kernel/01-topology-euler-operators` and the boolean material in `kernel/08`.

Technique: B-rep adjacency is a graph: a coedge knows its next/prev around a loop, its partner across an edge, and the radial cycle of coedges sharing a non-manifold edge. The two hottest kernel inner loops are (1) imprint, which finds where two bodies' faces intersect and splits edges/faces, and (2) classification, which decides for each face fragment whether it is inside, outside, or on the other body, by walking adjacency and shooting rays. Both are dominated by data-dependent loads: "follow this index, read that entity, decide where to go next." Each hop is a potential cache miss because the next address is not known until the current load returns, defeating the prefetcher and serializing on memory latency. The mitigation is layout, not algorithm: keep the entities likely to be visited in one walk physically near each other (handle values that are close index into nearby arena slots), and pack into each visited entity exactly the fields the walk needs (next, partner, radial, bbox) so one cache line answers several hops. A defragmenting pass that renumbers handles after heavy editing restores locality the way a copying GC compacts a heap.

Limitations: You cannot fully linearize a general graph; some pointer chasing is irreducible. Renumbering handles to restore locality conflicts with handle stability (external references and persistent naming must survive), so compaction needs an indirection or remap table. Booleans create and destroy entities mid-operation, so locality decays exactly when you need it most.

Kernel relevance: This is the core reason Keel's arena layout matters more than its algorithms' big-O for medium models. Practical levers for Keel: allocate the coedges of a loop consecutively so a loop walk is near-linear; co-locate an edge's two coedges; pack the traversal fields (next, prev, partner, radial-next, cached bbox, surface handle) into the hot array so a radial walk touches one line per coedge, not five. Because booleans churn the arena, Keel should consider a post-imprint compaction of the working body (with a remap table preserving external handles) before the classification sweep, so the read-heavy classification runs over freshly localized data. This ties directly to the allocation-churn discussion in Part 8.

## PART 2: SIMD and vectorized evaluation

### Source: Bezier extraction as a matrix-form, GEMM-friendly NURBS evaluator (Borden, Scott, Hughes et al.)

Citation: M.J. Borden, M.A. Scott, J.A. Evans, T.J.R. Hughes, "Isogeometric finite element data structures based on Bezier extraction of NURBS," International Journal for Numerical Methods in Engineering 87 (2011) 15-47. Tech report: oden.utexas.edu/media/reports/2010/1045.pdf. Related: Scott et al. on T-spline Bezier extraction.

Technique: Bezier extraction precomputes, per knot span, a constant "extraction operator" matrix C that maps the global B-spline control points restricted to that span onto the Bernstein (Bezier) control points of that span. Once C is precomputed (it depends only on the knot vector, not on the evaluation point), evaluating the spline at parameter u reduces to: evaluate the fixed-degree Bernstein basis at the local coordinate, then a small dense matrix-vector or matrix-matrix product. The crucial property is that the Bernstein basis is the same low-degree polynomial set for every span and every patch, so its evaluation is a fixed unrolled kernel with no knot-vector branching, no de Boor recursion, no per-point search beyond the span lookup. Batched over many points or many patches, the operation becomes a tall dense GEMM (general matrix multiply): exactly the shape that BLAS, SIMD, and GPUs accelerate best. This converts the irregular, branchy de Boor recursion into a regular, branch-free, vectorizable matrix pipeline.

Limitations: The extraction operators cost memory (one matrix per distinct span) and a precompute pass; they must be invalidated and rebuilt when knots change (refit/insert). For one-off single-point evaluations the setup does not pay off; de Boor is fine. Rational NURBS still needs the homogeneous-divide post-step, which is not part of the linear GEMM. Extraction is most valuable when the same surface is evaluated at many points (tessellation, sampling, intersection marching), less so for sparse queries.

Kernel relevance: This is Keel's primary SIMD/throughput path for NURBS. For tessellation and dense sampling, precompute extraction operators per face once, then evaluate a grid of points as a batched Bernstein-times-control-points GEMM in SoA layout. It is branch-free (good for autovectorization and for any future GPU port), reuses the precompute across all sample points, and isolates the rational divide to a final vectorized step. Keel should keep de Boor for exact analytic work and sparse single-point queries, and switch to matrix-form evaluation for the high-volume batched cases. This is the single highest-leverage SIMD decision for the geometry layer.

### Source: SoA de Boor / de Casteljau batched evaluation and vectorized basis functions

Citation: Synthesis from the NURBS Book (Piegl & Tiller) evaluation algorithms read against SoA/SIMD practice (Acton; the Rust SoA sources above); de Casteljau and de Boor recurrence structure.

Technique: De Boor (for B-splines) and de Casteljau (for Bezier) are triangular recurrences: each level linearly interpolates adjacent control points with a blending weight derived from knots/parameters. The recurrence itself is inherently serial in depth (level k+1 needs level k), so you do not SIMD within one point's recurrence. You SIMD across points: lay out N evaluation parameters and their N intermediate control-point sets in SoA (all the x-coordinates of level-k contiguous, all y, all z), and run the recurrence as wide vector lanes, computing N points in lockstep. The same idea vectorizes basis-function evaluation: the Cox-de Boor basis values for a batch of parameters in the same span compute as parallel lanes. Bounding-box construction over a control net and predicate sign tests over batches of candidate pairs are similarly SoA-batchable: load 4 or 8 boxes, test against one query box with one comparison instruction.

Limitations: Batching requires that the points share enough structure (same patch, ideally same span) to keep lanes coherent; points in different knot spans branch differently and break lane uniformity unless sorted by span first. Triangular recurrence has a long dependency chain that limits ILP for any single point. Tail handling (point counts not a multiple of lane width) needs scalar cleanup. Gathering scattered control points into SoA has a cost that must be amortized over many evaluations.

Kernel relevance: Keel's tessellator and intersection sampler should evaluate per-patch point grids in SoA-batched de Boor/de Casteljau (or matrix-form per the previous source) rather than scalar per-point calls. Sorting sample points by knot span before batching keeps lanes coherent. Batched box tests accelerate the boolean broad-phase face-pair pruning. The rule: per-point scalar evaluation is the slow path reserved for true one-offs; everything that produces many points goes through a batched SoA kernel.

### Source: Portable SIMD in Rust, autovectorization realities (std::simd, the 2025 state)

Citation: Sergey "Shnatsel" Davidoff, "The state of SIMD in Rust in 2025" (shnatsel.medium.com); itamarst, "Using portable SIMD in stable Rust" (pythonspeed.com); rust-lang/portable-simd repo and beginners-guide; std::simd docs (doc.rust-lang.org/std/simd).

Technique: Rust offers three SIMD avenues. (1) Autovectorization: LLVM vectorizes simple, branch-free, bounds-check-free loops automatically; clean iterator chains over slices often vectorize with no SIMD code, and autovectorized code sometimes matches or beats hand-written SIMD. (2) `std::simd` (portable_simd): a target-independent `Simd<T, N>` abstraction that compiles to the best instructions per platform (SSE/AVX/NEON), but it is nightly-only as of 2025. (3) Stable explicit SIMD via `core::arch` intrinsics (architecture-specific) or the `wide`/`pulp`/`multiversion` crates, where `multiversion` compiles several CPU-feature variants and dispatches at runtime. Key practical caveats: floating-point autovectorization is unreliable on stable because reordering FP additions changes results, so LLVM will not reorder them without fast-math, which a precision kernel must not enable; and there is no built-in function multiversioning, so the `multiversion` crate is the stable way to get AVX2/AVX-512 paths.

Limitations: The portable path is nightly, forcing a stable kernel onto intrinsics or third-party crates. The exact constraint that protects determinism (no FP reassociation) is the same constraint that blocks the easiest autovectorization of reductions, so Keel cannot rely on the compiler to vectorize sums. Intrinsics are non-portable and unsafe. Runtime dispatch adds a branch and complicates inlining.

Kernel relevance: Keel should structure hot evaluation loops to autovectorize: SoA layout, slices not iterators-of-structs, hoisted bounds checks, no early returns inside the kernel, and `f32`/`f64` lanes explicit. For reductions that must be deterministic (any sum that feeds geometry), Keel must NOT let the compiler reassociate; it should use an explicit fixed-order vectorized reduction (see Part 4) rather than hoping for autovectorization. For broad portability without nightly, the `wide` crate or `core::arch` with `multiversion` dispatch is the pragmatic stable choice now, migrating to `std::simd` when it stabilizes. The non-reassociation rule is the hinge between this part and the determinism part.

## PART 3: Parallelism analysis specific to a kernel

### Source: OpenCASCADE parallel booleans (BOPAlgo), OSD_ThreadPool, the two-phase split

Citation: OCCT developer docs and forums: "Parallelizing BOPs" (dev.opencascade.org/content/parallelizing-bops); OSD_Parallel and OSD_ThreadPool class references; OCCT 7.3.0 release notes; BOPAlgo_PaveFiller / BOPAlgo_Algo::SetRunParallel.

Technique: OCCT's boolean algorithm is explicitly split into an Intersection Part (the PaveFiller: pairwise face/face, edge/face, edge/edge intersection that produces the section curves and "paves") and a Building Part (assembling the result shells from split faces). OCCT parallelizes primarily the Intersection Part, because it is a large set of largely independent pairwise computations: each candidate face pair can intersect in parallel. Parallelism is opt-in (`SetRunParallel`, disabled by default) and is driven either by Intel TBB or by OCCT's own built-in thread pool (`OSD_ThreadPool`), which holds a fixed set of threads alive in sleep state for the process lifetime to avoid spawn cost; TBB is used if linked, otherwise the ad-hoc pool. The Building Part is far less parallelized because it mutates and stitches shared topology, the serialization point.

Limitations: That parallelism defaults off and centers on intersection is a tell: the building/stitch phase resists safe parallelism in a mutable-shared-topology design, so OCCT's overall boolean speedup is bounded by Amdahl on the serial build. OCCT's threading is bolted onto a mutable C++ object graph with handle reference counting, so thread-safety is partial and historically fragile (shared handle refcounts, global state). The model is "parallelize the obviously independent part, leave the rest serial."

Kernel relevance: OCCT validates Keel's central map directly: intersection is read-mostly and parallelizes per face-pair; the build/stitch is the serialization point. Keel can do better than OCCT precisely because of copy-on-write: where OCCT must be cautious mutating a shared C++ object graph, Keel's intersection phase reads immutable input snapshots with zero locking, and the only serialized region is the final apply of topology edits to a fresh COW version. Keel should copy OCCT's two-phase decomposition (intersect, then build) and make the intersect phase fully parallel-read, while keeping the build phase a deliberate single-writer (or carefully partitioned) region.

### Source: Parasolid threading model (read-parallel, single-writer per partition) and PK concurrency

Citation: Parasolid PK documentation and threading guidance (Siemens), synthesized with the general partitioned-concurrency patents surfaced in search; cross-read with `kernel/25-parasolid-capability-map`.

Technique: Parasolid's published guidance treats the modeler as supporting concurrent read access to a partition while serializing modifications. The practical model used by Parasolid-based applications: multiple threads may interrogate (read) geometry concurrently, and parallelism across independent operations is achieved by giving each thread its own partition/session of bodies so there is no shared mutable state between threads. Within a single modeling operation that mutates one body, the operation is effectively single-writer. The unit of safe parallelism is therefore "independent bodies in independent partitions," not "two threads mutating one body."

Limitations: This is coarse-grained parallelism: it scales when you have many independent parts (assembly-level batch operations) but does not by itself speed up one large boolean on one body. It pushes the burden of partitioning onto the application. Details of Parasolid's internal threading are proprietary; the public contract is essentially "reads concurrent, writes isolated per partition."

Kernel relevance: Parasolid's model is the conservative, proven baseline Keel must at least match: per-body and per-partition parallelism is always safe and should be the default way Keel parallelizes assemblies and batch jobs (regenerate 200 features across independent bodies on a thread pool). Keel's COW topology makes the "independent partitions" model natural: each immutable snapshot is a partition any number of readers can share. Keel can then go beyond Parasolid by adding intra-operation read-parallelism (the intersection phase) on top of this inter-operation parallelism, because COW guarantees the inputs cannot change under a reader.

### Source: Rayon work-stealing vs structured parallelism in Rust

Citation: Niko Matsakis / rayon-rs, the Rayon crate (docs.rs/rayon); generalistprogrammer.com Rayon guide; Guillaume Endignoux, "Optimization adventures: making a parallel Rust workload 10x faster with (or without) Rayon" (gendignoux.com, 2024).

Technique: Rayon provides data parallelism via a fixed-size work-stealing thread pool built on a `join(a, b)` primitive and parallel iterators (`par_iter`). Work is recursively split into tasks; idle threads steal tasks from busy threads' deques, giving automatic load balancing without the programmer scheduling anything. `par_iter().map().reduce()` parallelizes a map-reduce; `join` parallelizes a divide-and-conquer. Rayon enforces Rust's `Send`/`Sync` at compile time, so data races are caught by the type system. Endignoux's case study shows the practical caveats: naive `par_iter` can be slower than serial when tasks are too fine-grained (steal and synchronization overhead dominates) or when there is false sharing; the fix is coarser chunks (`par_chunks`), reducing allocation, and minimizing cross-thread contention, yielding up to 10x.

Limitations: Work-stealing makes the order of reduction and task completion nondeterministic, which is the direct enemy of bitwise reproducibility (Part 4). Rayon's global pool can interfere with itself under nesting. Fine-grained tasks have real overhead; speedup requires right-sized work units. Rayon does not help with the serialized topology-write phase.

Kernel relevance: Rayon is the natural engine for Keel's parallel-read phases: `par_iter` over candidate face pairs in the boolean broad/narrow phase, over faces in tessellation, over patches in batched evaluation. The compile-time `Send`/`Sync` checking is a major safety asset given Keel's correctness bar. But Keel must control where Rayon's nondeterminism is allowed: it is fine for independent map work whose outputs are later merged in a deterministic order, and forbidden where reduction order would change floating-point results. The discipline is "parallel map, deterministic merge," developed next.

### Source: Copy-on-write persistent topology as the membrane for lock-free parallel reads

Citation: Read-Copy-Update literature (InfoQ "RCU: the Secret to Lock-Free Performance"); persistent B-tree / path-copying (Andrew Johnson, "What is a persistent B-tree?"; Sarnak-Tarjan fat nodes); SurrealDB VART snapshot-isolation post; Concurrency Freaks on immutable structures.

Technique: A persistent (copy-on-write) data structure makes updates by path copying: to change a node you allocate fresh copies of the nodes along the root-to-leaf path you touch and leave every untouched subtree shared by reference, producing a new root that shares almost everything with the old. The two roots are both valid, immutable snapshots. Readers pin a root (an `Arc` in Rust) and traverse with no locks at all, because the version they hold can never be mutated; a writer builds a new version in parallel and publishes it by swapping the root pointer. This is the structural basis of RCU and of snapshot isolation: lock-free, wait-free reads coexisting with a single writer, with old snapshots remaining consistent until their last reader drops them.

Limitations: Path copying allocates on every edit and creates garbage (old paths) that must be reclaimed when readers finish, which `Arc` refcounting handles but at a cost. Memory overhead grows if many versions are retained. Write throughput is single-writer per structure (multiple concurrent writers need a merge or partitioning strategy). Pointer-rich persistent structures can have worse cache locality than a flat mutable array.

Kernel relevance: This is the architectural keystone that makes Keel's safe-parallelism map work. Because topology is COW, the boolean's input bodies are immutable snapshots that any number of intersection/classification threads read lock-free, with zero risk of a concurrent edit corrupting a traversal. The serialized write phase produces a new version by path-copying only the affected shells/faces, sharing the rest. This is precisely why Keel can promise both heavy read-parallelism and correctness: the COW snapshot is the membrane separating the parallel read world from the serial write world. The `Arc`-pinned-root pattern is the Rust-native expression of RCU here.

## PART 4: Determinism under parallelism

### Source: Demmel, Nguyen, Ahrens et al., reproducible floating-point summation and ReproBLAS

Citation: J. Demmel, H.D. Nguyen, "Fast Reproducible Floating-Point Summation" (ARITH 2013) and follow-ups; P. Ahrens, J. Demmel, H.D. Nguyen, "Efficient Reproducible Floating Point Summation and BLAS" (UC Berkeley EECS-2016-121); ReproBLAS library (bebop.cs.berkeley.edu/reproblas). Related: "Numerical reproducibility for the parallel reduction on multi- and many-core architectures" (Parallel Computing, 2015).

Technique: The problem they solve: floating-point addition is non-associative, so `(a+b)+c` can differ from `a+(b+c)` in the last bits; a work-stealing reduction sums partials in whatever order threads finish, so the bitwise result varies run to run and thread-count to thread-count. ReproBLAS computes a sum that is independent of the order of summation. The core device is a "pre-rounding" / binned superaccumulator: each input is split across a small fixed set of bins keyed by exponent range, additions within a bin are exact (no rounding), and the final result is assembled from the bins in a canonical order. The accumulator is a few floating-point words (about 6), the cost is roughly a small constant times n additions, and the result is reproducible regardless of how the work was split or scheduled, while still allowing tiling and vectorization. It is order-independent by construction, not by forcing a serial order.

Limitations: Reproducible summation costs more than naive summation (several-fold on the reduction itself, though often negligible against surrounding work). It solves summation/dot-product/BLAS-level reductions, not arbitrary order-dependent algorithms (it will not make a hash-ordered loop deterministic). Integrating a superaccumulator into every kernel reduction is intrusive.

Kernel relevance: This is the rigorous answer to "how do we get parallel speedup without order-dependent floating point" that Keel's determinism promise demands. Wherever Keel reduces in parallel and the bits matter (centroid/mass-property accumulation, summed areas/volumes, fitting residuals, any parallel `reduce`), Keel should either (a) use a reproducible/binned summation so the answer is order-independent, or (b) reduce in a fixed deterministic tree order. ReproBLAS shows option (a) is feasible without giving up vectorization or tiling. This directly discharges part of the `kernel/14` determinism contract for the numerical reductions.

### Source: Deterministic reduction/merge order on top of nondeterministic work-stealing

Citation: Synthesis of Rayon's scheduling semantics (Part 3) with the reproducibility constraint (above) and the determinism dossier `kernel/14`; reinforced by the parallel-reduction-reproducibility paper cited above and Rayon's documented deterministic-result property under fixed split structure.

Technique: The reconciliation pattern is "nondeterministic schedule, deterministic result." You let the work-stealing scheduler run tasks in any order for load balancing, but you make the observable result independent of that order by two means. First, structure the reduction so the combine operation is applied in a fixed, schedule-independent order: Rayon's `reduce` combines along the same recursive split tree regardless of which thread did which leaf, so if the split structure is deterministic (depends only on input length, not on timing) and the combine is associative-by-construction (integer, or reproducible-sum), the output is bit-stable. Second, never let parallelism leak hash iteration order or thread IDs into results: sort by a stable geometric key (entity handle, lexicographic coordinate) before any order-sensitive step, so the merge order is defined by data, not by arrival time. The result: the same input gives the same bits on 1 thread or 64.

Limitations: This forbids the cheapest tricks: you cannot reduce in arrival order, cannot iterate a `HashMap` and emit in that order, cannot let a thread-local first-come-first-served winner decide ties. Enforcing deterministic split structure can reduce load-balancing freedom slightly. It requires discipline at every reduction and every map-with-side-output, and is easy to violate accidentally (one stray `HashMap` traversal breaks it).

Kernel relevance: This is Keel's operational rule for the whole parallel layer, and it ties straight to `kernel/14`. Concretely: (1) parallel-map freely (intersection, evaluation, tessellation), but (2) collect outputs into handle-sorted vectors before merging, (3) reduce numeric accumulators with reproducible/fixed-order sums, (4) ban `HashMap`/`HashSet` iteration from any path that produces ordered output (use `BTreeMap` or sort), and (5) make every split decision depend only on data sizes. With these, Keel keeps work-stealing's speedup and still honors the bitwise-reproducible-across-thread-counts promise. This is the determinism-vs-speed resolution.

## PART 5: GPU offload candidates and their limits

### Source: Krishnamurthy, Khardekar, McMains, direct GPU evaluation of NURBS curves and surfaces

Citation: A. Krishnamurthy, R. Khardekar, S. McMains, "Direct Evaluation of NURBS Curves and Surfaces on the GPU" (ACM Symposium on Solid and Physical Modeling, SPM 2007); extended in "Optimized GPU evaluation of arbitrary degree NURBS curves and surfaces" (Computer-Aided Design, 2009). PDF: mcmains.me.berkeley.edu/pubs/SPM07KrishnamurthyKhardMcMains.pdf.

Technique: They store a NURBS surface's control points and knot vectors as textures in GPU memory and run a fragment (pixel) program that, for each fragment representing a parametric sample (u,v), evaluates the surface point directly from those textures using the basis-function recurrence on the GPU. Because every fragment is independent, the GPU evaluates an entire grid of surface points in massive parallel, achieving large speedups over CPU evaluation for dense sampling. The 2009 extension generalizes to arbitrary degree and optimizes the basis evaluation. This is the canonical demonstration that dense, regular surface evaluation is an ideal GPU workload: same kernel, many independent points, arithmetic-heavy, no branching on shared state.

Limitations: It targets dense regular sampling for rendering/visualization, not the exact, adaptive evaluation a kernel needs for intersection. GPU floating point historically differed from CPU (rounding, transcendental approximations), breaking bitwise determinism and exact-predicate guarantees. The host-to-device transfer of control nets and back-transfer of points has fixed latency that only amortizes for large batches. It computes points, not the topology or the exact section curves.

Kernel relevance: This is the textbook GPU offload candidate for Keel and also the textbook limit. Dense tessellation sampling and visualization-grade surface evaluation map cleanly to the GPU and could give large throughput for display and coarse sampling. But Keel's exact intersection, classification, and predicate work must stay on the CPU: GPU FP non-reproducibility violates the determinism promise, and irregular adaptive marching is GPU-hostile. The realistic verdict: GPU as an optional accelerator for tessellation/display, never on the exact-modeling critical path.

### Source: Schollmeyer & Froehlich, direct trimming of NURBS surfaces on the GPU; GPU trimmed-NURBS ray casting

Citation: A. Schollmeyer, B. Froehlich, "Direct Trimming of NURBS Surfaces on the GPU" (ACM SIGGRAPH 2009). PDF: uni-weimar.de Virtual Reality publications. Precursor: Pabst et al., "Ray Casting of Trimmed NURBS Surfaces on the GPU" (2006). Successor: Sloup & Havran, "Optimizing Ray Tracing of Trimmed NURBS Surfaces on the GPU" (CGF 2021). Background: Guthe, Balazs, Klein, "GPU-based trimming and tessellation of NURBS and T-spline surfaces" (2005).

Technique: Trimmed NURBS rendering must, for each surface sample, decide whether it lies inside the trim region defined by trim curves in parameter space. Schollmeyer & Froehlich split each trim curve into monotone segments in u and v and use an optimized bisection to classify a parameter point against each monotone segment without an actual intersection test, all inside a single GLSL shader integrated with GPU NURBS ray casting. Guthe's earlier approach encodes the trim region as a "trim texture" dynamically adapted to required resolution and trims during tessellation via alpha blending. Both make the expensive trimmed-surface display problem real-time on the GPU. Sloup & Havran later optimize the ray-tracing variant with better culling and Newton iteration.

Limitations: These are rendering/visualization techniques: they answer "is this display sample trimmed away," at pixel precision, not "what is the exact trimmed boundary topology." Trim textures are resolution-limited and leak at curve boundaries; shader bisection is fast but not the exact, adaptive root-finding a kernel's intersector needs. They assume a GPU pipeline and target frames, not modeling correctness.

Kernel relevance: For Keel, these define the precedent and the boundary of GPU usefulness. A future Keel viewer can render trimmed NURBS directly on the GPU using these methods, avoiding CPU tessellation latency for display. But the exact trimmed-boundary computation (the section curves, the trimmed-face topology) stays on the CPU with exact predicates. The lesson echoes the previous source: GPU for display-grade trimmed-surface rendering, CPU for exact trimmed-modeling. They are complementary, not substitutes.

### Source: The GPU verdict for a precision kernel (what maps, what does not)

Citation: Synthesis of the two GPU sources above with the host/device transfer-cost literature and the exactness/determinism constraints from `kernel/11` (exact predicates) and `kernel/14` (determinism).

Technique: The decision framework that emerges: GPU wins on massively parallel, arithmetic-dense, branch-light, error-tolerant work, surface and curve evaluation at dense samples, tessellation, ray/curve sampling for distance fields and visualization, BVH broad-phase traversal, signed-distance-field computation. GPU loses on irregular topology surgery (the boolean stitch, Euler operators: data-dependent pointer chasing with serial dependencies), exact predicates (need deterministic, often arbitrary-precision arithmetic the GPU does not provide bit-faithfully), and serial marching (intersection curve tracing where each step depends on the last). Host-device transfer adds a fixed latency that only pays off when the offloaded batch is large enough to dwarf the round trip.

Limitations: The frontier moves: GPGPU compute (CUDA/compute shaders) with `fma` control can be made more reproducible than fixed-function GPUs of 2007, and double-precision GPU support has improved. But "more reproducible" is not "bitwise identical across CPU and GPU and across GPU vendors," which is what a hard determinism promise needs. Maintaining a GPU path doubles implementation and testing surface.

Kernel relevance: Keel's realistic verdict: keep the entire exact-modeling core (booleans, predicates, intersection, classification, topology) on the CPU where determinism and exactness are controllable, and treat the GPU as an optional, clearly-bounded accelerator for tessellation, display, and coarse sampling/distance-field queries whose results never feed back into exact topology. This keeps the determinism promise intact and avoids coupling correctness to GPU driver behavior. GPU offload is a post-1.0 viewer/visualization concern, not an M7b kernel-core concern.

## PART 6: Lazy and incremental evaluation

### Source: Self-adjusting computation and Adapton (Acar; Hammer et al.)

Citation: Umut A. Acar, "Self-Adjusting Computation" (PhD thesis, CMU 2005) and "Self-Adjusting Computation with Delta ML"; M. Hammer et al., "Adapton: Composable, Demand-Driven Incremental Computation" (PLDI 2014) and miniAdapton/microAdapton; Acar et al. on selective memoization.

Technique: Self-adjusting computation builds a dynamic dependence graph during a computation: it records which inputs each result read. When inputs change, it does not recompute from scratch; it propagates the change through the dependence graph, recomputing only the affected nodes and reusing memoized results for unaffected ones, potentially turning a full recompute into work proportional to the change. Adapton refines this with demand-driven (lazy) recomputation: results are recomputed only when their value is actually requested, and a dirty-flag propagation marks downstream results stale on input change. Memoization and change-propagation are combined so that a small edit to a large computation costs roughly the size of the affected sub-computation, not the whole.

Limitations: The dependence-tracking machinery has overhead in time and memory; for computations that always change wholesale it is pure cost. Building a general self-adjusting runtime is heavy; most systems adopt a restricted, hand-rolled version. Fine-grained dependence tracking can itself become the bottleneck if dependencies are dense.

Kernel relevance: This is the theoretical backbone for Keel's lazy caches and incremental rebuild. The pattern Keel needs is the restricted, practical version: each derived artifact (a face's bounding box, its tessellation, its derivatives, the BVH) records the durable definition it depends on (the face's surface and trim), and an edit invalidates exactly the downstream caches. After a local edit (a fillet on two faces), only those faces' tessellations and the BVH leaves over them are recomputed, the rest reused. Keel does not need a full Adapton runtime; it needs the dependence discipline: durable definition plus rebuildable cache with precise invalidation, which is also the `kernel/14` pattern.

### Source: Salsa (Rust incremental framework) and the durable-definition-plus-rebuildable-cache pattern

Citation: Salsa framework (salsa-rs, used by rust-analyzer); Ilya Lakhin, "Salsa Algorithm Explained" (Medium). Conceptual kin: build systems (Bazel, Shake) and the "functional core, memoized query" model.

Technique: Salsa structures a program as a set of "queries" (pure functions) over "inputs." It memoizes every query result keyed by its arguments and tracks which other queries/inputs each query read (the dependency graph). When an input changes, Salsa bumps a global revision and uses red-green marking: a query is "green" (reusable) if none of its dependencies changed since its result was computed, else it is re-executed; crucially, if a re-executed dependency produces the same value, downstream queries can still be reused (early cutoff). This gives precise, automatic incremental recomputation with minimal recompute and is the engine behind rust-analyzer's responsiveness on edits to large codebases.

Limitations: Salsa imposes a query/input architecture (pure functions, interned keys) that not all code fits; mutation-heavy or pointer-graph code needs reshaping. Memoization tables consume memory proportional to retained results. The dependency tracking adds per-query overhead, paying off only when reuse is high.

Kernel relevance: Salsa is the concrete, Rust-native template for Keel's cache layer and a proof it scales to real systems (rust-analyzer). Keel's evaluated geometry, bounding boxes, tessellations, derivative caches, BVHs, mass properties, fit naturally as "queries" over the durable topology "inputs." On an edit, Keel bumps a revision; caches whose dependencies are unchanged stay green and are reused; early cutoff means an edit that does not actually move a face leaves its tessellation valid. Whether Keel adopts Salsa directly or implements the same red-green discipline by hand, this is the recommended structure for the lazy-cache layer: durable definition as input, rebuildable cache as memoized query, revision-based precise invalidation.

### Source: Incremental BVH refit vs rebuild at the data-structure level

Citation: Cross-reference to `kernel/08` BVH material (Kopta et al. refit/rotations, Bittner et al. incremental update), considered here at the cache/data level rather than the algorithm level.

Technique: After a local edit, the spatial acceleration structure can be refit (keep the tree topology, recompute bounding boxes bottom-up along the paths touching changed leaves, O(changed) work) or rebuilt (discard and reconstruct, O(n) but restores tree quality). At the data-structure level the relevant choices are: store BVH nodes in a flat array (SoA: child indices, min/max corners as parallel arrays) so a refit is a cache-friendly bottom-up sweep over contiguous memory; keep a leaf-to-node back-index so a changed face updates only its path to the root; and track a quality metric (e.g., SAH cost drift) to decide when accumulated refits have degraded the tree enough to justify a full rebuild. Refit reuses the existing allocation (no churn); rebuild reallocates.

Limitations: Repeated refits without rebuild degrade tree quality (boxes inflate, overlap grows), slowly raising query cost until a rebuild is forced. Refit needs the leaf-to-node mapping maintained across edits, extra bookkeeping. A flat-array BVH that shares structure with a COW topology snapshot complicates invalidation.

Kernel relevance: Keel's BVH belongs in the Salsa-style cache layer as a refit-first, rebuild-on-degradation artifact. Store it as a flat SoA node array for cache-friendly refit. After a local boolean or fillet, refit the touched paths (cheap, allocation-free); track a degradation metric and trigger a full parallel rebuild (Part 3) when quality drops. This connects the incremental-cache discipline (this part) to the allocation discipline (Part 8): refit avoids churn, rebuild is a deliberate, batched reallocation.

## PART 7: Large-model and out-of-core memory

### Source: GigaWalk and the UNC Walkthrough lineage (massive-model rendering as a memory strategy)

Citation: W.V. Baxter, A. Sud, N. Govindaraju, D. Manocha, "GigaWalk: Interactive Walkthrough of Complex Environments" (Eurographics Workshop on Rendering 2002), gamma.cs.unc.edu/GIGAWALK; the broader UNC Walkthrough / massive-model-rendering program (gamma.web.unc.edu). Modern descendants: UltraMeshRenderer (ACM TOG 2025), GPU out-of-core CAD frameworks.

Technique: GigaWalk renders gigabyte-scale environments (the Double Eagle tanker: 82M triangles, 127K objects, 4 GB) interactively by combining three memory/throughput strategies: a unified scene graph over which it runs (1) spatial clustering of geometry into a hierarchy, (2) conservative occlusion culling so out-of-view geometry is never touched, and (3) levels-of-detail so distant objects use coarse representations. Geometry that does not fit in core is paged from disk on demand, prefetched along the predicted view path, and represented at the coarsest LOD that meets a pixel-error bound. The key insight for memory (not just display): LOD and culling decide what must be resident, so the working set is bounded by what is visible-and-near, not by total model size. This is out-of-core management driven by a spatial hierarchy plus a residency policy.

Limitations: GigaWalk targets rendering, where pixel-error LOD and occlusion are valid simplifications; a modeling kernel cannot simplify the geometry it must compute on exactly. The system assumed specialized 2002 hardware (dual SGI pipelines). Occlusion culling and view-dependent paging assume a viewpoint, which exact modeling operations do not have.

Kernel relevance: The transferable idea is residency management by spatial hierarchy plus a working-set policy, not the rendering specifics. For assemblies too large for RAM, Keel can keep full exact B-rep only for the bodies a current operation touches, and hold the rest as lightweight proxies (bounding boxes, coarse facets, lazy handles) paged from disk, faulting in full topology only when an operation actually references a body. LOD-for-memory means storing a cheap proxy per body and the durable definition on disk, materializing exact geometry on demand. The spatial hierarchy that drives clash/broad-phase (Part 9) doubles as the residency index: only bodies whose boxes interact with the operation's region need be resident.

### Source: Memory footprint per entity, streaming/paging topology, and 64-bit handle considerations

Citation: Synthesis of the slot-map/arena memory model (Part 8) with the out-of-core strategy above and Keel's stated generational-handle design; informed by general out-of-core CAD frameworks (e.g., GPU out-of-core rendering of massive CAD models, ResearchGate 2016).

Technique: The per-entity footprint sets the ceiling on in-core model size, so it must be budgeted: a coedge with packed traversal fields (a handful of 32- or 64-bit indices plus a cached box) might be tens of bytes; multiplied by hundreds of millions of entities in a giant assembly, the arena must either fit in RAM or page. Paging topology means the arena's backing store can spill cold slots to disk (memory-mapped or an explicit page cache) while hot slots stay resident, with the generational handle as a stable logical address that survives paging (the generation guards against stale references to evicted-and-reused slots). Handle width is a real decision: 32-bit indices cap an arena at ~4 billion slots per type (ample for one body, marginal for a giant flattened assembly), while 64-bit handles remove the ceiling at the cost of doubling index memory and halving cache-line index density. A common compromise: 32-bit index plus a separate generation, packed into 64 bits, scoped per partition so each body's arena stays in 32-bit range.

Limitations: Memory-mapping an arena and paging cold slots interacts badly with pointer-chasing traversals that jump unpredictably (a page fault mid-radial-walk stalls everything), so paging works best when hot working sets are spatially clustered (ties to Part 1 locality). 64-bit handles cost cache density exactly where Part 1 wants it dense. Generation counters must be wide enough not to wrap within a session.

Kernel relevance: Keel should budget per-entity bytes deliberately (hot fields packed, cold fields paged), scope arenas per body/partition so 32-bit indices suffice within a body while a wider partition+body+index handle addresses an unbounded assembly, and make the arena backing store pageable for out-of-core assemblies. The generational handle is already the right abstraction: it is a stable logical address independent of physical residency, which is exactly what a paging system needs. This unifies the handle design with the out-of-core requirement.

## PART 8: Allocation strategy

### Source: Slot-maps and generational arenas in Rust, performance characteristics

Citation: `slotmap` crate (Orson Peters); `generational-arena` crate; Manish Goregaokar, "Arenas in Rust" (manishearth.github.io, 2021); Lucas S., "Generational indices guide" (Medium); mooman219/generational_arena_bench; oneuptime, "How to Optimize Memory with Arena Allocators in Rust."

Technique: A slot-map/generational arena stores entities in a contiguous `Vec` of slots; each slot holds a value plus a generation counter and a free-list link. Insertion reuses a free slot (or pushes) and returns a `key` = (index, generation). Access checks that the slot's current generation matches the key's; if the slot was freed and reused, the generation mismatches and the stale key is rejected, solving the ABA/dangling-reference problem without per-object lifetime tracking. The performance profile: allocation is O(1) amortized and touches only the arena (no global allocator call per entity), values are contiguous for cache-friendly iteration, and deletion is O(1) (push to free list). `slotmap` offers secondary maps to attach extra data keyed by the same key (the natural home for cold/attribute data, Part 1). Benchmarks show generational arenas vastly outperform per-object `Box`/`Rc` allocation for churn-heavy workloads, with iteration speed near a plain `Vec`.

Limitations: The generation check adds a branch per access. Free-list reuse can scatter live entities over the arena after heavy delete/insert churn, eroding the contiguous-iteration benefit (motivating compaction, Part 1). `slotmap` uses unsafe internally; `generational-arena` is safe but slightly slower. Secondary maps for cold data add an indirection. Generation counters can in principle wrap.

Kernel relevance: This is exactly Keel's chosen topology store, and the analysis confirms it is the right call: O(1) churn-friendly allocation, contiguous iteration for the SoA traversal loops, and stale-handle safety via generations, which is also a correctness asset (a dangling reference into deleted topology is caught, not silently wrong). The secondary-map feature is the implementation vehicle for hot/cold splitting from Part 1: hot fields in the primary slot-map, cold attributes in secondary maps. The churn-scatter limitation is the concrete reason for the post-boolean compaction recommended in Part 1.

### Source: Arena/bump allocation, custom allocators in Rust, minimizing boolean allocation churn

Citation: Manish Goregaokar, "Arenas in Rust" (typed-arena, bumpalo); `bumpalo` crate; Rust `allocator_api` / `Allocator` trait; oneuptime arena-allocator guide.

Technique: Bump allocation (e.g., `bumpalo`) allocates from a large pre-reserved block by simply advancing a pointer: allocation is a pointer add, and there is no per-object free; the entire arena is dropped at once. This is ideal for the transient, short-lived intermediate data a boolean generates (candidate pair lists, section-curve segments, temporary classification fragments): allocate them all in a per-operation bump arena, then reset the arena in one move when the operation finishes, instead of thousands of individual `malloc`/`free` calls. Rust's `Allocator` trait (allocator_api) lets collections like `Vec` be parameterized by a custom allocator, so a `Vec<_, &Bump>` allocates inside the bump arena. The principle: separate long-lived durable topology (the slot-map arenas, which persist) from short-lived operation scratch (a bump arena, reset per operation), so the durable store never fragments from transient churn.

Limitations: Bump arenas cannot free individual objects (all-or-nothing reset), so they suit phase-scoped scratch, not long-lived heterogeneous data. Over-reserving wastes memory; under-reserving forces new blocks. The `Allocator` trait is still unstable on stable Rust as of writing, requiring nightly or wrapper crates. Mixing allocators complicates lifetimes.

Kernel relevance: This is Keel's allocation-churn answer for booleans, the operation that creates and discards the most transient data. Keel should run each boolean (and each heavy local operation) with a per-operation bump arena for all scratch: pair lists, section segments, temporary fragments, classification work. Durable results graduate into the persistent slot-map (COW) version; the bump arena resets in one shot at operation end, eliminating thousands of allocator calls and the fragmentation they cause. This pairs with the slot-map source: persistent topology in generational arenas, transient operation scratch in bump arenas, the two never churn each other.

## PART 9: Algorithmic complexity and scaling

### Source: Boolean broad-phase, O(n log n) vs O(n^2), and spatial pruning of face pairs

Citation: Synthesis of the BVH/box-filtering material in `kernel/08` (face-pair candidate generation, box filtering) with the OCCT two-phase boolean (Part 3) and general computational-geometry sweep/hashing results; reinforced by the intersection-part-is-the-cost observation from OCCT.

Technique: The naive boolean tests every face of body A against every face of body B: O(n_A * n_B), quadratic, fatal at scale. The standard fix is a broad phase that prunes to plausibly-intersecting pairs before any exact intersection: build a BVH (or spatial hash, or sweep-and-prune) over each body's face boxes and query for overlapping boxes, reducing candidate pairs to roughly O((n + k) log n) where k is the number of actually-overlapping pairs (typically near the surface-contact region, far smaller than n^2). Only surviving candidate pairs go to the expensive exact face/face intersection. The constants matter as much as the exponent here: a tight, cache-friendly box test (SoA, SIMD, Part 2) on millions of pairs is what makes the broad phase cheap in practice, and the broad-phase result feeds the parallel intersection map (Part 3).

Limitations: Broad-phase wins assume the actual intersection set k is small relative to n^2 (true for typical boolean contacts, false for deeply interpenetrating or coincident-face cases where k approaches n^2). BVH build cost is itself O(n log n) and must be amortized or cached (Part 6 refit). Degenerate cases (many coplanar faces) defeat box pruning and must fall back to specialized handling.

Kernel relevance: Keel's boolean pipeline must be broad-phase-first by construction: BVH over each body, box-overlap query to generate candidate pairs, then parallel exact intersection only on survivors. This is what turns the boolean from O(n^2) into near-O(n log n) and is the difference between a kernel that handles 10K-face parts and one that handles 1M-face imports. The broad phase is also the natural parallelism and residency boundary (Parts 3 and 7): candidate pairs are the independent work units, and only bodies whose boxes overlap need be resident.

### Source: Where real kernels spend time, profiling wisdom, and the constants that matter

Citation: Synthesis of OCCT's "intersection part is the parallelized/expensive part" (Part 3), the memory-bound-layout findings (Part 1), and general profiling wisdom (the criterion/flamegraph/cachegrind sources, Part 10).

Technique: The empirical pattern across kernels: time concentrates not in clever high-level algorithms but in (1) exact surface/surface intersection and root-finding on candidate face pairs, (2) the memory-latency cost of pointer-chasing adjacency traversal during imprint and classification, and (3) repeated surface evaluation during sampling/marching. The constants that matter are cache behavior and FP-evaluation count, not asymptotic class, for the medium models that dominate real use. The profiling discipline: never optimize by intuition; measure with a profiler, find the actual hot function (often a surprise, e.g., a bounding-box recompute or an allocator call, not the "interesting" math), and confirm whether it is compute-bound or memory-bound (cachegrind tells you) before choosing SIMD (compute) vs layout (memory) as the fix.

Limitations: Profiles are workload-specific; the hot spot for a fillet-heavy part differs from a boolean-heavy import. Microbenchmarks can mislead if they use unrepresentative inputs (Part 10). Premature asymptotic optimization can lose to constant-factor cache wins and vice versa.

Kernel relevance: This sets Keel's optimization priorities in order: first get the broad-phase complexity right (Part 9), then fix the memory layout of the traversal/imprint/classification hot paths (Part 1, the likely dominant cost on real models), then SIMD the evaluation (Part 2), and only then chase micro-optimizations, each step gated by an actual profile. The warning is concrete: Keel should expect the real hot spots to be adjacency traversal and surface evaluation, and should measure rather than assume, because the "interesting" boolean math is often not where the time goes.

## PART 10: Benchmarking methodology for a kernel

### Source: Criterion.rs statistical microbenchmarking, with flamegraph/cachegrind/perf profiling

Citation: `criterion` crate (Brook Heisler, bheisler/criterion.rs); `iai`/`iai-callgrind` for instruction-count benchmarks; cargo-flamegraph; criterion-perf-events; profiling walkthroughs (Ritik Chopra, "Profiling Rust Like a Pro"; LambdaClass, "Benchmarking and analyzing Rust performance with Criterion and Iai").

Technique: Criterion runs each benchmark many times, discards warmup, and applies statistical analysis (bootstrap confidence intervals, outlier detection) to estimate the true mean and, crucially, to detect and size regressions/improvements against a saved baseline, so a CI run can flag "this commit slowed `boolean_union` by 8% (p<0.05)." It generates gnuplot reports. The recommended three-stage profiling stack: (1) Criterion microbenchmarks for statistical rigor on specific functions; (2) flamegraphs (`cargo flamegraph --bench`) to see where wall-clock time goes across the whole operation; (3) cachegrind/callgrind (via Valgrind, surfaced by `iai-callgrind`) for deterministic instruction counts and cache-miss rates (e.g., a 12% L1-miss rate flags a layout problem). Instruction-count benchmarks (Iai) are noise-free and CI-stable where wall-clock timing is noisy on shared runners.

Limitations: Criterion's wall-clock timing is sensitive to machine noise (thermal, neighbors), making cross-machine regression tracking unreliable, hence the value of instruction-count benchmarks for CI. Microbenchmarks measure functions in isolation and miss whole-pipeline and cache-warming effects. Valgrind-based tools run ~50x slower, limiting how large a model you can profile under them.

Kernel relevance: Keel should adopt Criterion for microbenchmarks (per-evaluator, per-predicate, per-traversal-primitive), Iai/callgrind instruction counts for noise-free CI regression gates, and flamegraph + cachegrind for diagnosing whether a hot spot is compute- or memory-bound (which decides SIMD vs layout per Part 9). The CI gate catches performance regressions the way the differential tests in `kernel/08` catch correctness regressions: a commit that doubles cache misses in the classification walk should fail the build.

### Source: Representative macro-benchmarks and the danger of benchmarking only easy cases

Citation: Synthesis of the test-corpus material in `kernel/08` (ABC dataset, Fusion 360 Gallery, Thingi10K, STEP zoos) repurposed from correctness testing to performance benchmarking, with general benchmarking-honesty wisdom.

Technique: Microbenchmarks alone lie about real performance because they exercise small, clean inputs. A kernel needs macro-benchmarks on representative real models: boolean operations on actual imported STEP parts (with their messy trimming, near-tangencies, and high face counts), tessellation of full assemblies, classification on parts with many small features. The corpora used for correctness testing (ABC's million CAD models, the Fusion 360 Gallery, Thingi10K, STEP interoperability zoos) double as a performance suite: track wall-clock and instruction counts on a fixed representative subset across releases. The honesty discipline: deliberately include the hard cases (large face counts, coincident faces, near-tangent intersections, dirty imported geometry) because those are where real kernels slow down or fall over, and a benchmark suite that omits them gives false confidence and lets regressions hide in exactly the cases users hit.

Limitations: Macro-benchmarks are slower to run and noisier, harder to attribute a regression to a specific cause (need profiling to localize). Large corpora are expensive to run every commit, forcing a representative-subset choice that may miss some regressions. Real models have licensing/distribution constraints.

Kernel relevance: Keel's benchmark suite must be two-tier: fast Criterion/Iai microbenchmarks on every commit (evaluators, predicates, traversal) plus a curated macro-benchmark set of real STEP parts and assemblies (drawn from ABC/Fusion 360 Gallery/Thingi10K and Keel's own regression corpus) run on releases and nightly, deliberately weighted toward hard cases (high face count, coincident/tangent geometry, dirty imports). This is the performance analogue of the robustness-corpus discipline in `kernel/08`: measure on what breaks kernels, not on what flatters them, and gate releases on both correctness and performance regressions.

## Performance architecture for Keel (synthesis)

The layout decisions. Keel stores topology in per-entity generational slot-maps (already chosen, and confirmed optimal: O(1) churn, contiguous iteration, stale-handle safety). On top of that arena, apply Acton-style data-oriented layout: split each entity's fields into a hot, SoA-packed primary array holding exactly the traversal-critical fields (next/prev coedge, partner, radial-next, cached bounding box, surface handle) and a cold secondary map holding attributes, persistent-name tags, and provenance, so the radial/coedge walk and box tests touch one cache line per entity, not five. Allocate the coedges of a loop and the two coedges of an edge consecutively for traversal locality, and run a post-imprint compaction (with a handle remap table preserving external references) before the read-heavy classification sweep, so classification streams over freshly localized data. Persistent topology lives in the slot-maps; all transient boolean scratch (candidate lists, section segments, temporary fragments) lives in a per-operation bumpalo arena that resets in one move at operation end, so durable and transient data never churn each other.

The safe-parallelism map of the boolean pipeline. Decompose the boolean into OCCT's two phases and exploit copy-on-write as the membrane. (1) Broad phase: BVH over each body's face boxes, box-overlap query to generate candidate face pairs, turning O(n^2) into near-O(n log n); this is the unit of parallel work. (2) Intersection/narrow phase: read-only over immutable COW input snapshots, so every candidate pair intersects in parallel via Rayon `par_iter` with zero locking and zero risk of concurrent mutation, the big speedup. (3) Classification: also read-parallel over the immutable inputs plus the section results. (4) Build/stitch phase: the single serialization point, a deliberate single-writer region that path-copies only the affected shells/faces into a fresh COW version, sharing everything untouched. Inter-operation parallelism (independent bodies/partitions on a thread pool, the Parasolid model) wraps all of this for assemblies. The rule: parallelize reads aggressively, serialize the topology write deliberately, let COW snapshots separate the two worlds.

The determinism-vs-speed resolution. Keep work-stealing's load balancing but make every observable result schedule-independent. Parallel-map freely; collect outputs into handle-sorted vectors before any merge; reduce all geometry-affecting numeric accumulators with reproducible/binned summation (ReproBLAS-style) or a fixed deterministic tree order, never arrival order; ban `HashMap`/`HashSet` iteration from any path that produces ordered output (use `BTreeMap` or sort by stable geometric key); make every Rayon split decision depend only on data sizes, not timing; and forbid FP reassociation in the compiler (no fast-math) so SIMD never silently changes bits. Result: the same input yields the same bits on 1 thread or 64, honoring the hard API promise from `kernel/14` while still getting near-linear read-phase speedup.

The GPU verdict. Keep the entire exact-modeling core (booleans, predicates, intersection, classification, topology surgery, serial marching) on the CPU, where determinism and exactness are controllable and where the irregular pointer-chasing work lives anyway. Treat the GPU as an optional, clearly-bounded accelerator for tessellation, trimmed-NURBS display rendering (Schollmeyer/Guthe), dense surface evaluation (Krishnamurthy), and coarse sampling/distance fields, results that drive the viewer and never feed back into exact topology. GPU FP non-reproducibility across vendors makes it incompatible with the determinism promise on the critical path. GPU offload is a post-1.0 visualization concern, not an M7b core concern.

The lazy-cache discipline. Structure all derived geometry (bounding boxes, tessellations, derivative caches, BVHs, mass properties) as Salsa-style memoized queries over durable topology inputs, with revision-based precise invalidation and early cutoff: an edit bumps a revision, only caches whose durable dependencies actually changed recompute, an edit that does not move a face leaves its tessellation valid. The BVH is a refit-first, rebuild-on-degradation artifact stored as a flat SoA node array: cheap allocation-free refit on local edits, deliberate parallel rebuild when a tracked quality metric drifts. This is the durable-definition-plus-rebuildable-cache pattern shared with `kernel/14`. For batched evaluation, precompute Bezier-extraction operators per face and evaluate point grids as branch-free SoA GEMM kernels (autovectorized on stable Rust via clean slice loops, or `wide`/`core::arch` with `multiversion` dispatch, migrating to `std::simd` when stable), reserving scalar de Boor for exact single-point queries.

What to measure. Two-tier benchmarking gated in CI. Fast tier: Criterion statistical microbenchmarks plus Iai/callgrind instruction-count benchmarks (noise-free, CI-stable) on evaluators, predicates, and traversal primitives, run every commit with regression gates. Slow tier: a curated macro-benchmark set of real STEP parts and assemblies (from ABC, Fusion 360 Gallery, Thingi10K, and Keel's regression corpus), deliberately weighted toward hard cases (high face count, coincident/tangent geometry, dirty imports), run on releases and nightly. Diagnose every hot spot with flamegraph (where time goes) and cachegrind (compute- vs memory-bound) before choosing SIMD (compute) or layout (memory) as the fix, and expect the real hot spots to be adjacency traversal and surface evaluation, not the "interesting" boolean math. Optimization priority order: broad-phase complexity first, then traversal/imprint/classification memory layout, then evaluation SIMD, then micro-optimizations, each gated by a profile.

The through-line: a B-rep kernel is a data-parallel numerical engine bolted to a serial graph-mutation engine. Keel wins by giving the numerical engine SoA layout, batched SIMD evaluation, and lock-free parallel reads over COW snapshots, while keeping the graph-mutation engine serial, deterministic, and exact. Copy-on-write is the keystone that lets both be true at once, and determinism discipline at every reduction is the price of the API promise.
